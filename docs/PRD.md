# iDuoPreviewer 产品方案

## 0. 设备参数状态

**iPhone Duo 是苹果于 2026-09-09 正式发布的真机型号**（首款折叠屏 iPhone），并非概念机或占位假设。内外屏的分辨率、像素密度、比例已通过官方发布信息核实无误（见下方 Sources），6.1 的设备参数表和配置 JSON 可以直接作为视觉稿和开发的依据，不再是"待确认"状态。

仍然保留"设备参数配置化"这个技术方案（不写死在组件代码里），原因变成了纯工程上的考虑：一是安全区的**精确像素值**（灵动岛具体宽高、状态栏/手势条高度、圆角半径等）官方发布信息里只给了定性描述、没有逐像素的数字，做视觉稿时大概率还要实测微调；二是这套配置化结构本身也是为后续多机型扩展打基础（见 10.多机型扩展）。

## 1. 产品定位

一个轻量级网页工具：让设计师/开发者/产品经理快速看到"一张图片 / 一个 PDF / 一个网页"放到 iPhone Duo 的**内屏**或**外屏**里实际显示是什么样子，不用等真机、不用切设备。

**核心价值**：所见即所得的设备级预览，尤其是内外屏比例不同这个差异点，是这个工具存在的意义。

**目标用户**：UI设计师、H5/网页开发、应用截图/商店素材制作者、内容运营（确认海报图在小屏上不被裁切）。

---

## 2. 核心使用场景

1. 设计师做好一张宣传图，想看看在 Duo 外屏（更小更方）上文字会不会被裁掉 → 上传图片，切到外屏视图。
2. 开发做了一个 H5 活动页，想确认在内屏的安全区（刘海/灵动岛、圆角、Home Indicator）下内容有没有被遮挡 → 输入网址，内屏视图，打开安全区遮罩。
3. 产品经理要在评审会上快速对比同一份 PDF 封面在两种屏幕上的观感 → 上传 PDF，来回切换内外屏，甚至左右并排看。

## 3. 页面结构（信息架构）

整体上下两段式，符合你的基本需求：

```
┌─────────────────────────────────────────┐
│  顶部条：产品名 + 内外屏切换按钮           │
├─────────────────────────────────────────┤
│                                           │
│              预览区（上半部分）            │
│         设备外框 + 内容渲染 + 工具条        │
│                                           │
├─────────────────────────────────────────┤
│         上传 / 网址输入区（下半部分）        │
│   [拖拽上传区]   [网址输入框 + 前往按钮]     │
└─────────────────────────────────────────┘
```

- 桌面端：预览区占视口约 60-70% 高度，输入区固定在底部，滚动时预览区可选择"吸顶"以保持可见。
- 移动端（用手机浏览器打开这个工具本身）：预览区和输入区都收窄为单栏，预览区高度按设备框比例自适应，避免超出首屏太多。

## 4. 功能模块详细设计

### 4.1 预览区

**设备外框（Device Frame）**
- 用 SVG/CSS 画出接近真机的外框：圆角、边框、刘海或灵动岛（如内屏有）、摄像头孔（外屏如有）。
- 外框内是一个精确按设备比例裁切的"画布"，内容在画布内按不同填充模式展示。
- 提供"仅看内容不看外框"的简洁模式开关，方便截图用于交付物。
- **外屏是 D 形非对称屏幕**（右侧边框更窄、左侧边框更宽，因为要给铰链让位），不能用简单的四角等半径圆角矩形实现，需要用 SVG path 或 CSS `clip-path: path(...)` 分别定义四个角/两侧的圆角半径和边距，内屏则是标准的四角对称圆角（详见 6.1 设备参数表）。

**内容渲染，按类型区分**
| 类型 | 渲染方式 | 说明 |
|---|---|---|
| 图片 (jpg/png/webp/gif/svg) | `<img>`，支持 `object-fit: cover/contain` 切换 | 提供"铺满裁切"和"完整显示留边"两种模式对比 |
| PDF | pdf.js 渲染到 canvas，支持翻页 | 默认显示第 1 页，可翻页；也可选"作为长图连续滚动" |
| 网页 (URL) | `<iframe>` 嵌入 | 见 4.1.3 风险说明，需要兜底方案 |

**缩放与填充模式**
- Contain（完整显示，可能有留白）
- Cover（铺满裁切，可能裁掉边缘）
- 原始尺寸 1:1（超出部分可滚动，用于精确检查像素级细节）
- 默认用 Contain，图片类默认给用户切换按钮。

**安全区辅助层（MVP 功能，体现专业度）**
- 工具条上放一个开关，打开后在设备框内叠加**半透明色块浮层**，直观标出刘海/灵动岛区域、折叠铰链/手势条区域等不可安全放置内容的地方，帮助用户一眼判断内容是否会被系统 UI 遮挡。
- 建议不同区域用不同色块区分（比如顶部安全区一种颜色、底部手势条一种颜色），并配简短图例说明每块颜色代表什么。
- 内屏和外屏各自独立配置安全区范围，切换内外屏时浮层跟随联动切换，不需要用户重新开关（同样走 6.1 的配置化方案）。
- 浮层默认关闭，避免影响用户第一眼看内容效果，需要时手动开启。

**预览区工具条**（悬浮在设备框上方或旁边）
- 内外屏切换按钮（见 4.2，也可以在这里放一份，跟顶部呼应）
- 填充模式切换
- **安全区辅助层开关**（MVP）
- 亮/暗背景切换（模拟系统深色模式下的呈现，仅对网页/PDF有意义）
- 下载预览效果图（把当前设备框+内容合成导出为 PNG，方便直接甩进汇报文档）
- 清空/重置按钮

**网页预览的技术风险与兜底方案（需要明确告知用户）**
- 大量网站设置了 `X-Frame-Options` 或 `Content-Security-Policy: frame-ancestors`，会导致 iframe 无法加载（白屏或浏览器报错）。这是网页预览类工具的通病，不是本产品的 bug，需要提前做好体验设计：
  1. iframe 加载超时（如 5 秒）后，检测不到内容加载成功，展示友好提示："该网站不支持被嵌入预览，可尝试截图模式"。
  2. **截图模式（推荐作为主方案之一）**：后端调用无头浏览器（Puppeteer/Playwright）对目标 URL 截图，返回图片再放进设备框预览。优点是几乎兼容所有网站；缺点是需要服务端能力、有一定延迟和成本，且是静态快照不能滚动交互。
  3. MVP 阶段可以两者都做：先尝试 iframe 实时嵌入（交互性好），失败则自动降级为截图模式。

### 4.2 内外屏切换按钮

- 位置：预览区右上角一个醒目的分段控制器（Segmented Control），如「内屏 | 外屏」。
- 切换时设备外框比例、安全区参数、可能的默认填充模式一起切换，带一个平滑的宽高过渡动画（如 200-300ms ease），避免视觉跳变。
- 图片/PDF/网页内容本身不重新上传或重新加载，只是重新按新的画布比例排版渲染。
- 进阶：提供「内外屏并排对比」模式（第三个选项，双设备框左右展示同一内容），方便一次性对比差异，这是这个工具区别于通用设备模拟器的亮点功能，建议放进 V1.1 而不是 MVP，先把基础切换做稳。

### 4.3 上传区

- 拖拽上传 + 点击选择文件，两种方式都支持。
- 支持类型：图片（jpg/png/webp/gif/svg）、PDF。做好类型和大小校验（比如限制单文件 20-50MB，具体看是否有后端处理网页截图，纯前端渲染图片/PDF可以放宽）。
- 上传后不需要真的传到服务器：图片/PDF 可以用 `URL.createObjectURL` 或 FileReader 在浏览器本地渲染，不落盘、不经过网络，兼顾隐私和速度。除非产品希望做"生成分享链接"这种协作功能，才需要真正上传到存储。
- 上传成功后自动切到"文件已选中"状态，显示文件名+大小+一个"更换文件"按钮，避免用户误以为还要点别的按钮才生效。
- 错误提示要具体：格式不支持 / 超出大小限制 / 文件损坏无法解析，分别给不同文案。

### 4.4 网址输入区

- 一个输入框 + "预览"按钮，支持回车提交。
- 基本校验：自动补全协议头（用户输入 `example.com` 自动处理成 `https://example.com`）、格式非法时给出提示。
- 加载态：请求中显示 loading，网址预览通常有延迟（尤其走截图模式时），要有清晰的进度反馈，不能让用户以为卡死。
- 历史记录（锦上添花项）：本地记住最近输入过的几个网址，方便反复调试同一个页面时快速切换。

### 4.5 上传区与网址区的关系

- 二者可以做成 Tab 切换（"上传文件" / "输入网址"），或者始终并排展示（如你原始需求描述的"上传和网址输入区"并列）。建议做成左右并排（桌面端）/ 上下并排（移动端），减少一次多余点击，且用户能一眼看出这个工具支持两种输入方式。
- 无论走哪种输入方式，只要有新内容替换旧内容，预览区都要立刻更新，不需要用户额外点"应用"按钮（除了网址需要手动点"预览"或回车提交，因为这是一次网络请求）。

### 4.6 横竖屏切换（MVP 功能）

- 位置：工具条新增一个横屏/竖屏切换按钮（图标切换，如竖放/横放手机图标），与内外屏切换按钮并列展示，但两者相互独立、可自由组合（内屏竖屏、内屏横屏、外屏竖屏、外屏横屏，共 4 种组合）。
- 交互：点击后设备外框整体旋转 90°（宽高互换），复用 4.2 里已有的宽高过渡动画，保持切换体感一致。
- 内容适配：填充模式（Contain/Cover）在横屏下按新的宽高比重新计算，不需要用户重新设置；图片/PDF/网页内容本身不重新加载。
- **安全区浮层的横屏处理**：灵动岛/屏下摄像头这些区域的物理位置是固定的，横屏时它们相对内容的位置会偏向左侧或右侧（取决于手机是向左转还是向右转），不能简单地把竖屏安全区参数旋转 90° 推导出来。MVP 阶段建议做**简化处理**：只支持一个固定的旋转方向（约定为"Home 键/ 底部在右"的传统横屏方向），不做双向镜像切换，把这个简化写进配置注释里；双向切换可以作为后续小优化补充。
- 对应到 6.1 的设备参数配置，每个 `ScreenProfile` 需要额外补充一套横屏安全区参数（不是从竖屏参数自动换算，而是单独定义），详见 `TECH_SPEC.md`。

### 4.7 多语言 / 国际化（新增功能，已实现）

MVP 上线后新增的功能，原始范围内未规划，现已完成开发：

- 右上角提供语言切换控件（分段控制器风格，与内外屏切换按钮视觉呼应），支持 **英文 / 中文** 两种语言。
- 首次访问默认使用英文；用户手动切换后，选择结果记忆在浏览器 `localStorage` 中，下次打开自动沿用上次选择，不需要重复设置。
- 覆盖范围：页面全部文案（顶部标语、工具条按钮、空状态/加载态/异常态提示、Toast 错误文案、上传区/网址输入区文案、页脚联系区块等），不存在中英文混杂的遗漏文案。
- 语言包缺失某个 key 时回退到英文，避免出现空白文案。
- 技术方案见 `TECH_SPEC.md` 对应章节；未来若要新增语言（如日语、繁体中文），只需要在 `src/i18n/locales/` 下新增一份语言包文件并注册到语言列表，不需要改动业务组件代码。

### 4.8 分屏效果预览（未来功能，非 MVP，见第 8/10 节）

iPhone Duo 内屏支持系统级左右分屏多任务，这是它区别于普通直板 iPhone 的另一个差异点，未来可以加进来，让用户体验"两个内容分屏摆在内屏上"是什么效果，思路先记录：

- 需要**两组**独立的预览内容输入（各自可以是图片/PDF/网址），不是当前 MVP 单一 `PreviewSource` 就够用的。
- 内屏画布按分屏比例左右切分（可能支持用户拖动调整左右分屏比例，或先固定为常见的 1:1 / 7:3 等预设比例），中间加一条分屏分隔线。
- 分屏模式目前只对内屏有意义（外屏尺寸小，系统通常不支持分屏），交互上可以做成：切到内屏时，工具条多一个"分屏预览"开关，打开后上传/网址输入区跟着变成左右两组。
- 工作量比 4.1-4.6 的单内容预览明显更大（状态管理、UI 布局都要翻倍），建议放在 V1.2+，等 MVP 稳定后再评估是否排期。

## 5. 交互与状态设计

**空状态**：首次打开时预览区展示设备框 + 引导性占位内容（比如印着"上传图片/PDF 或输入网址开始预览"的示意文案），不要空白一片。

**加载状态**：
- PDF 首次解析、网页截图/iframe 加载，都需要 loading 指示（骨架屏或 spinner）。
- 超时/失败要有重试按钮，而不是无声失败。

**异常状态**：
- 文件格式不支持
- 文件过大
- 网址无法访问（DNS 失败/超时/被目标网站拒绝嵌入）
- PDF 加密或损坏无法渲染

**多标签会话**（如果做 PDF 多页）：
- 翻页控件放在设备框下方，页码指示 + 上一页/下一页，支持键盘方向键。

## 6. 技术方案建议

### 6.1 设备参数配置化（关键设计）

不要把 iPhone Duo 的宽高比、圆角半径、安全区写死在组件代码里，而是抽成一份独立的配置数据。

**设备参数表（2026-09-09 苹果官方发布信息确认，见第 0 节 Sources）**

| | 内屏（展开主屏） | 外屏（闭合小屏） |
|---|---|---|
| 物理分辨率（宽×高） | 1878 × 2670 px | 1398 × 2034 px |
| 像素密度 | 430 PPI | 460 PPI |
| 对角线尺寸 | 7.6"（矩形实测 7.58"） | 5.4"（矩形实测 5.36"） |
| 面板类型 | 折叠 OLED，屏下前置摄像头，无挖孔 | 普通 OLED，带灵动岛 |
| 宽:高比例 | 1878:2670 ≈ 1 : 1.4218（约 1:√2，简化比 313:445，你给的近似值为 21:30） | 1398:2034 ≈ 1 : 1.455（精确简化比 233:339） |
| 顶部安全区 | 无刘海，仅极小状态栏安全边距 | 灵动岛占用，与常规 iPhone 一致（需要视觉稿阶段确定具体像素，暂用近似机型如 iPhone 16 Pro 灵动岛尺寸估算） |
| 底部安全区 | 折叠铰链区无系统安全区，仅保留手势条高度 | 标准底部手势条安全边距 |
| 左右安全区 | 左右均匀对称 | **不对称**：右侧边框更窄、安全边距更小；左侧边框更宽（D 形屏，给铰链让位） |
| 折痕/中线 | 不属于安全区，App 可铺满整条中线 | 不适用 |

> 注：内屏比例你给出两种表述——按物理分辨率算约为 313:445（≈1:1.4218），你标注的"精确比例 21:30"（=1:1.4286）与像素值略有出入，差异很小（<0.5%），不影响视觉呈现，配置里以物理分辨率 1878×2670 算出的比例为准；外屏两种表述（1398:2034 与 233:339）互相吻合，直接采用。

      "safeArea": {

好处：
1. 安全区精确值后续修正时，只改配置不改代码。
2. 为将来扩展"支持更多机型"（比如同时支持 iPhone 标准款、其他折叠屏手机）打好基础，产品可以从"单设备工具"平滑升级成"多设备预览工具"。

### 6.2 前端技术栈建议

- 框架：React/Vue 均可，纯预览+文件处理类工具，用 React + Vite 或 Vue3 + Vite 都是轻量合理的选择，看你团队熟悉度。
- PDF 渲染：`pdf.js`（Mozilla 官方库，成熟稳定）。
- 图片处理：原生 `<img>` + CSS `object-fit`，无需额外库。
- 文件拖拽上传：可用原生 Drag & Drop API 自己实现，工具量不大不一定需要引入第三方库。
- 设备外框：优先用 SVG + CSS clip-path/mask 实现，方便后续换比例和圆角。
- 导出预览图：`html2canvas` 或浏览器原生的 `Element.captureStream`/直接对 canvas 内容导出（若是 canvas 渲染的话更直接）。

### 6.3 网页截图兜底方案（如果要做）

- 需要一个轻量后端服务（Node + Playwright，或使用现成的第三方截图 API 服务）。
- 出于成本和访问频率考虑，建议对同一 URL 做短时缓存（比如 10 分钟内重复请求直接复用截图），并对请求频率做限流，防止被滥用当作免费截图服务。
- 需要考虑目标网站的合法性/合规性问题：不代理、不缓存明显违规内容，必要时加一层简单的 URL 黑名单或用户协议声明。

### 6.4 隐私与安全

- 图片/PDF 优先纯前端本地处理，不上传服务器，减少隐私顾虑，也是这个工具的一个卖点，可以在页面上明确写出来（"文件仅在你的浏览器本地渲染，不会上传到服务器"），增加用户信任度。
- 若做网址截图功能，明确告知这部分需要请求经过服务端。
- 输入网址要做基本的 SSRF 防护（服务端截图服务不能被用来探测用户内网地址，比如过滤 localhost/内网 IP 段/file协议等）。

## 7. 视觉设计建议

- 整体风格偏工具型产品：克制、留白多、视觉重心在设备框本身，UI 本身不抢戏。
- 设备外框用深色/中性色（如接近真机的太空灰/黑），预览区背景用浅灰或可切换深浅色，避免图片本身的颜色和背景色冲突导致误判。
- 内外屏切换按钮要有明显的"当前选中态"视觉反馈（比如底部下划线或填充背景），因为这是核心功能，不能让用户找不到或误以为切换没生效。
- 移动端适配：这个工具本身大概率也会被人用手机打开体验，所以下半部分的上传/网址区在小屏上要保证按钮可点击区域够大（不小于 44x44pt 这个苹果标准）。
